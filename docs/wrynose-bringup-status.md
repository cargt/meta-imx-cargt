## Issues found and resolved

1. **Missing `CONFIG_SPL_HAVE_INIT_STACK` across all board defconfigs.** Without it, `_main()` uses an untrained-DRAM stack address before `board_init_f`, causing a hard SPL hang on real hardware. Found via JTAG on the primary board, confirmed missing on every other board. Fixed in all 5 in-scope boards' defconfigs (required a second pass on `imx91-cargt-00363-00365` — see orphaned-patch issue below).
2. **Dangling `&lcdif` overrides + legacy `u-boot,dm-spl`/`u-boot,dm-pre-reloc` tags** (`00324-00326`, `00359-00406`). U-Boot's DT doesn't model `lcdif`, and only `bootph-*` tags are recognized by `fdtgrep`'s SPL-DTB pruning in 2026.04 — without the migration, the pruned SPL DTB was silently reduced to ~13 lines.
3. **Stale `imx9_eeprom.h` include** (`00359-00406`) left behind by an eeprom-rename patch, causing implicit-declaration build errors.
4. **Missing `IMX_BOOT_IMAGE_GUID` definition + duplicate `dm_usb_gadget_handle_interrupts()`/`regulators_enable_boot_on()`** (`imx8mp-00377-00365`) — upstream now provides both generically.
5. **Unbounded `while()` poll on DYN_REF mode-register bits** in `ddr_init.c`, new in 2026.04 — bounded with a timeout instead (cargt's DDR config sets the bit that triggers this path).
6. **Missing serial console/bluetooth aliases** (`00324-00326`, `00359-00406`, `imx91-00363-00365`, `imx8mp-00377-00365`). Without them, the console UART's dynamic `ttyLPx`/`ttymxcN` numbering doesn't reliably match u-boot's hardcoded `console=` bootarg — once `earlycon`'s clock is swept up by `clk: Disabling unused clocks`, the board hangs silently with no console output. Root-caused on `00324-00326` via a live hang, confirmed identical on the other three.
7. **Missing `opencl` in `DISTRO_FEATURES`** blocked `clinfo`'s build for `imx8mp-00377-00365` (never hit before since that board's full image had never been built in this tree).
8. **"No soundcards found" on `00324-00326`** — root-caused to a deployment gap, not a code/DT bug: `CONFIG_SND_SOC_FSL_SAI=m` (module) never had its `/lib/modules/` tree installed after a manual `Image`+`.dtb`-only file swap. Resolved by switching to full `.swu` deployment (bundles kernel+modules+rootfs correctly).
9. **`weston.service` crash-looping on `00359-00406`** — this board has no display hardware at all (confirmed via DTS inspection + user), but `weston` is installed unconditionally distro-wide via `DISTRO_FEATURES` wayland. Masked via `SYSTEMD_AUTO_ENABLE:pn-weston-init = "disable"` in the machine conf.
10. **U-Boot TCPC init failure on `imx93-cargt-00359-00406`** (`tcpc_init: Can't find bus` / `setup_typec: tcpc port1/port2 init failed, err=-22`). U-Boot's own DTS never modeled the PTN5110 TCPC chips or PCA9555 GPIO expander the kernel DTS has on `lpi2c3`, and board C code hardcoded `i2c_bus = 1` (aliased to the never-enabled `lpi2c2`) instead of `2` (`lpi2c3`'s real alias per `imx93.dtsi`). Added the missing `&lpi2c3` node + pinctrl groups matching the kernel DTS, and corrected the bus index. Verified via the compiled `.dtb` that `pca9555_21`/`ptn5110`/`ptn5110_2` now resolve correctly under the `i2c2` alias, and **confirmed on real hardware** — `TCPC: Vendor ID [0x1fc9], Product ID [0x5110]` now reads back correctly on both ports.
11. **Orphaned duplicate patch series silently absorbing a real fix.** `recipes-bsp/u-boot/u-boot-imx/` contained two entire patch series both numbered 0001-0026 — one active (referenced by `SRC_URI`), one a stale/unreferenced DDR-timing series from an earlier branch that happened to reuse the same filenames. The `CONFIG_SPL_HAVE_INIT_STACK` fix for `imx91-cargt-00363-00365` landed in the orphaned copy and was never actually built. Removed all 26 orphaned files (confirmed unreferenced anywhere in the tree first) and re-applied the fix to the real, active patch — verified via `cleansstate` rebuild that the option is now actually set in the built `.config`, and now confirmed via a full eMMC flash boot on real hardware (clean boot, `mmcpart=1`, no failed systemd units, both eth0/eth1 register without error in Linux).
12. **`imx93-cargt-00324-00326`: kernel Bluetooth never bound to `hci0`.** `0004-Add-device-tree-files-for-00324-00326.patch`'s `&lpuart5` node enabled `fsl,uart-has-rtscts` but never added the `bluetooth { compatible = "nxp,88w8997-bt"; ... }` child node the `btnxpuart` serdev driver needs to bind — same class of bug as the earlier `00363-00365` bluetooth fix (see item 1 in the kernel-side history), just never ported to this board. Added the missing node (`fw-init-baudrate`/`max-speed` = 3000000, matching the `00363` reference). Confirmed on hardware: `hci0` now appears where it previously didn't.
13. **`imx93-cargt-00324-00326`: entire `usdhc3` (WiFi/BT SDIO) controller was missing from the DTS.** Unlike `usdhc1` (eMMC) and `usdhc2` (SD card, explicitly `no-sdio`), this board's DTS had no third SDIO host for the M.2 wireless module at all — confirmed via dmesg showing the `mlan`/`moal` driver load but never see a card, and via schematic review showing the module's `WL_REG_ON`/`BT_REG_ON` enable lines are wired through this board's `pca9555@20` I2C GPIO expander (pins 13 and 10 respectively), not a bare SoC GPIO like `00363-00365` uses. Added: a `&usdhc3` node with `pinctrl_usdhc3`/`pinctrl_usdhc3_wlan` groups (dedicated SD3 SoC pads, same physical pins as every other board using USDHC3), a `usdhc3_pwrseq` (`mmc-pwrseq-simple`, `reset-gpios = <&pca9555 10 ...>` for `BT_REG_ON`), a `reg_usdhc3_vmmc` fixed regulator (`gpio = <&pca9555 13 ...>` for `WL_REG_ON`), and a `wifi_wake_host` interrupt child bound through the `pca9555`'s own interrupt-controller capability (added `interrupt-controller;`/`#interrupt-cells = <2>` to the existing `pca9555` node, which didn't have them). Confirmed on hardware: `mmc2: new UHS-I speed SDR104 SDIO card at address 0001` — the module's SDIO function now enumerates correctly. **Mid-fix bug caught and corrected before it shipped**: the `usdhc3`/pinctrl content was initially inserted into the wrong patch hunk (the SOM-level `imx93-cargt-00324.dtsi` instead of the carrier-level `imx93-cargt-00324-00326.dts`), and that hunk's `@@` header/diffstat were left stale, causing `do_patch` to genuinely truncate the file on the next build. Caught via a DTC syntax error, fixed by recomputing both hunks' real line counts.

14. **`imx8mp-cargt-00377-00365`: U-Boot proper never booted at all — silent hang between BL31 and BL33, first-ever wrynose hardware test for this SoC family.** SPL and ATF/BL31 both completed cleanly every time (DDR trained, EEPROM read back correctly, BL31 handed off to entry point `0x40200000` matching `CONFIG_TEXT_BASE` exactly), but U-Boot proper's own banner never printed — not even the earliest possible output. Root-caused by diffing against NXP's own `imx8mp_evk_defconfig`: this board's defconfig never set `CONFIG_SYS_MALLOC_F_LEN` (U-Boot proper's own pre-relocation early-malloc pool, used for tasks like unflattening the devicetree before full malloc is available), leaving it at the smaller Kconfig default (`0x10000`) instead of the EVK's `0x18000` — and this board's devicetree carries considerably more content than the reference EVK's. Confirmed via a `DEBUG=1` ATF rebuild that BL31's handoff itself was correct (ruling out a FIT/packaging issue) before landing on this fix. **Mid-fix mistake caught before it shipped**: the first attempt set only `CONFIG_SYS_MALLOC_F_LEN`, not realizing Kconfig's default for `CONFIG_SPL_SYS_MALLOC_F_LEN` (the separate SPL-stage pool, already correctly sized) falls back to the same value when not pinned explicitly — this silently bumped SPL's pool too, shifting its memory layout enough to turn a previously-clean DDR training pass into a mid-training hang on the very next hardware test. Fixed by pinning both values explicitly and independently. **Same session, ported four real bug fixes from scarthgap** (commit `cd0640d`, validated there on real Kingston- and Micron-populated hardware): a TCPC/USB-C `board_init()` fix (inverted `#ifdef`, wrong GPIO expander address, a nonexistent EVK-only PD-switch probe, and a fastboot-blocking early-return on unconfirmed CC/PD state), a hardcoded FEC PHY address removal, EEPROM `dram_rank` write/repair support, and a vendor-neutral DDR timing dispatch (by size/speed/rank, with a blank-EEPROM fail-safe bootstrap). Two hunks needed rebasing for 2026.04 API drift (a `board_init()` ifdef-block reorder, and `cpu_func.h` replacing the removed `common.h` include) — otherwise unchanged from the validated scarthgap fixes. **CONFIRMED on real Micron-populated hardware (2026-07-24)** via SDP/USB boot: full U-Boot banner, both TCPC ports read back correct Vendor/Product ID (`0x1fc9`/`0x5110`), both Ethernet MACs detected, and fastboot comes up successfully over a bench USB cable without a confirmed CC/PD sink state — exactly the behavior the ported fix intended.

## Issues found, noted for future resolution

1. **`imx91-cargt-00363-00365`: EQOS ethernet fails to probe in u-boot** (`eqos_probe_resources() failed: -38`/ENOSYS), only the FEC interface comes up. U-Boot's `imx91.dtsi` correctly overrides `&eqos`/`&fec` clocks to i.MX91-specific IDs in parallel fashion, and both are registered in the shared `clk-imx93.c` driver — yet only FEC works. Likely a gap in NXP's upstream i.MX91 EQOS clock support. Non-blocking (boot completes fine, Linux fully unaffected on both interfaces). Not yet root-caused to the exact failing clock call — would need u-boot rebuilt with `DEBUG` enabled in `dwc_eth_qos_imx.c` plus a hardware retest.
2. **`imx91-cargt-00363-00365`: `Could not read CPU frequency: -38` / `CPU: ... at 0 MHz`.** Likely a *different* root cause than #1 — the A55 core clock table entries are registered unconditionally for both imx91/imx93 (unlike the gated ENET entries). Not investigated further. Non-blocking.
3. **`imx93-cargt-00359-00406`: `Could not read CPU frequency: -2` / `at 0 MHz`**, and a different `usdhc2` microSD pinout than the kernel DTS. Separate from the now-fully-resolved TCPC/DTS-staleness bug (see item 10 above) — not yet investigated. Worth checking whether the same DTS-staleness pattern that caused the TCPC bug also exists elsewhere in this board's u-boot DTS (e.g. the `usdhc2` pinout difference).
4. **`imx93-cargt-00363-00365` (primary board): DSI shearing bug** — display-related, paused in an earlier session, not revisited during this pass.
5. **`imx93-cargt-00324-00326`: cosmetic `fw_devlink` "Fixed dependency cycle(s)" warnings** (USB Type-C `tcpc@51`/`tcpc@52`, and the LVDS display chain) — everything downstream still binds/works, flagged as lower-severity DT modeling cleanup, not investigated further.
6. **`imx93-cargt-00324-00326`: this DUT's installed M.2 module (Murata Type 2EA) doesn't work with the image's WiFi driver stack.** After fixing the `usdhc3` DT gap (item 13 above), the SDIO card enumerates correctly (`04b4:bd31` vendor/device), but that's a Cypress/Infineon vendor ID — this image only builds NXP's `mlan`/`moal` driver (per this project's established IW610/IW612-only WiFi hardware baseline), so no driver claims the card and no `mlan0` interface appears. `brcmfmac` exists as kernel source but isn't built as a module in this config. Per user (2026-07-24): not a priority to chase right now. If revisited, would need `brcmfmac` + matching firmware enabled for chip ID `bd31`, and possibly different DT bindings for the wake/reg-on lines (`brcmfmac`'s bindings differ from the `nxp,wifi-wake-host` convention used elsewhere in this tree). Bluetooth (which per user needs WiFi powered up first on this module) remains untested end-to-end as a result, though the BT DT fix itself (item 12) is confirmed correct in isolation (`hci0` binds).
7. **`imx93-cargt-00324-00326` hardware erratum: console cable must be disconnected before reboot.** This board revision has a boot-pin conflict when anything is connected to the console UART at reset — confirmed by user, board hangs on reboot with the console cable attached. Not a software regression; remember to ask/confirm the cable is disconnected before issuing any remote `reboot` on this board.
